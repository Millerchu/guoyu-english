## P0 级

### P0-1 离线优先 + 服务端权威奖励 = 孩子的星星延迟到回家才有

**冲突位置**：3.1「即时正反馈」、5.2 各环节给星 ↔ 22.2 `COMPLETED_LOCAL`、23.4「奖励由服务端计算」

文档定的规则是：离线时客户端只能把状态标成「已完成·待同步」，星星必须等服务端聚合后才产生。那么孩子在车上、在公园完成五个步骤，奖励页是空的。

这直接打在核心设计原则「答对立即反馈、完成后有奖励」上。5–7 岁的孩子不会理解「待同步」是什么意思，他只知道「我学完了，没有星星」。

文档只在 10.5 提到月度汇总可显示「本地预测值」，**奖励本身没有任何乐观更新机制**。

**建议**：二选一并写进文档——
1. 客户端按与 `grantKey` 相同的规则本地记账，标记 `PENDING`，同步后以服务端结果为准做差额修正（推荐，符合儿童产品体验）；
2. 明确「离线不发星，只记进度」，并在 UI 上用孩子能懂的方式替代（例如「回家后打开宝箱」），但这会削弱离线场景的价值。

### P0-2 `grant_key` 粒度撑不起「每词 1 星」

**冲突位置**：5.2「跟我说：每词 1 星上限；读一句：1 星；小游戏：1–2 星」 ↔ 23.4「`grantKey` 由服务端按 `childId:learningDay:rewardRule` 生成」+ `UNIQUE INDEX uq_star_grant_child_key ON star_ledger(child_id, grant_key)`

按这个 key 的粒度，同一个 `rewardRule` 一天只能落一笔。5 个词各得 1 星，会被唯一索引吃掉 4 笔。

23.4 的原意是防「重复领取一次性签到奖励」，但把「一次性奖励」和「按对象累计的奖励」用同一个 key 规则处理了。

**建议**：拆成两类，分别定义 key——
- 一次性（签到、每日完成）：`childId:learningDay:CHECKIN`
- 按对象（跟读、认读）：`childId:learningDay:SPEAK_STAR:{itemId}`

### P0-3 第 11 章和第 24 章是两套互斥的 API

**第 11 章有、第 24 章没有**：
`/tasks/today`、`/tasks/{taskId}/items/{itemId}/complete`、`/speech/records`、`/games/{gameId}/submit`、`/phonics/today`、`/parent/dashboard`、`/parent/reports/weekly`、`/offline/manifest`、`/learning/calendar/{date}`

**第 24 章有、第 11 章没有**：
`/devices/pair`、`/content/packs`、`/content/packs/{id}/manifest`、`/sync/push`、`/sync/pull`、`/sync/status`、`/lessons/{id}`、`/parent/reports/monthly`

比接口清单更严重的是**两套设计哲学打架**：11 章是「在线直连 CRUD」（每完成一个 item 调一次 `complete`），24 章是「事件批量同步」（所有学习动作走 `/sync/push`）。这两个不能并存——如果动作只走 push，11 章的 complete 接口就是死代码；如果走 complete，离线 outbox 就失去意义。

**建议**：删掉第 11 章的接口表，只留第 24 章作为唯一实现口径，并补齐第 24 章缺的录音上传、游戏提交、拼读任务、家长 dashboard、周报。

### P0-4 第 10 章和第 23 章的表名、建模思路都不一样

| 第 10 章 | 第 23 章 |
| --- | --- |
| `course_unit` | `course_theme` |
| `lesson` | `lesson_step` |
| `learning_item` | `lexeme` |
| `daily_task` | `daily_checkin` |
| `learning_record` | `learning_event` |
| `mastery_record` | `word_mastery` |
| `book` / `book_page` | `picture_book` / `picture_book_page` |
| `book_reading_record` | `reading_progress` |
| `reward_record` / `badge` | `star_ledger` |

不只是改名，是两套模型：10 章是「任务驱动」（有 `daily_task`、`learning_record`），23 章是「事件驱动」（`learning_event` + 投影表）。离线同步只能建立在事件模型上。

同时 22.1 用 `Theme / Lesson / Step / Lexeme`，6.3 和附录 B 用 `Unit / Lesson / LearningItem`——**三套术语**。

**建议**：以 23 章为唯一权威；第 10 章降级为「概念模型」并删掉表名字段，或直接重写。术语统一到一套。

## P1 级

### P1-1 里程碑有三套，而且关键路径冲突

| 出处 | 离线同步排在哪 |
| --- | --- |
| 17.1 | **M4**（最后一步，做完 M1–M3 才做） |
| 27.3 | **M2**（第二步） |
| 20.8 | 阶段 4 |

17.1 的顺序最危险：它意味着 M1–M3 全部按「在线 CRUD」写，到 M4 再推翻重做成事件同步。**这是整个项目最贵的一次返工。**

**建议**：采用 27.3 的顺序。离线同步不是收尾功能，它是数据模型的一部分，必须前置。17.1 的 M0–M4 应作废或重写。

### P1-2 `learningDay` 时区口径自相矛盾

- 8.4：「依据**设备**记录的本地学习日期与时区，服务端校验」
- 22.4：「以儿童档案 `timezone_id`（默认 `Asia/Shanghai`）计算 `learningDay`」

设备时区 vs 档案时区。跨时区旅行、或孩子把平板时区改了，打卡日期就会漂。T10 专门测「时区边界」，但没说以谁为准。

**建议**：唯一口径 = 档案时区。设备时区只用于 UI 显示，不参与 `learningDay` 计算。

### P1-3 家长验证：「4 位 PIN」还是「强密码」

- 8.1：「4 位家长 PIN **或长按特定区域 3 秒**」
- 26.5：「家长身份验证使用**加盐强密码哈希**」

两个问题：

1. 4 位数字 PIN 只有 1 万种组合，加盐哈希防不住离线枚举，把它描述成「强密码」是自我安慰。
2. 「长按 3 秒」**不是验证**，任何孩子长按就进去了，直接违反 15 章「家长设置需要 PIN/家长验证，避免儿童误改」。

**建议**：删掉「长按 3 秒」。PIN 明确为 4–6 位 + 加盐 + 失败次数限制/递增延迟，并老实承认它的定位是「防误触」而不是「防破解」。

### P1-4 后端模块划分两套

- 9.2：11 个（auth / child / course / learning / book / phonics / game / reward / report / media / speech）
- 26.2：15 个（+ calendar / content / sync / common）

9.2 缺的恰好是离线架构的三个核心模块。**以 26.2 为准**，9.2 应作废。

### P1-5 性能指标两套

- 16 章：首页首屏 **< 2 秒**
- 27.2：局域网首次加载 **< 3s**

**建议**：统一到 3s。低端平板首次加载 + 解码图片，2s 不现实；如果一定要 2s，需注明「缓存命中后的二次加载」。

### P1-6 「游戏」到底是不是一级入口

- 4.1 一级导航有独立的「游戏」tab
- 第 7 章 13 张原型里**没有独立游戏页**，小游戏在 7.4 属于今日学习流程
- 22.3：小游戏内容由课程 JSON 生成，是课程内环节

同一个东西有两种定位：自由练习入口 vs 课程内必做步骤。这会影响 tabBar 结构和打卡判定（自由玩的小游戏算不算完成今日任务？）。

**建议**：明确「游戏」tab = 自由练习，不计打卡；课程内小游戏 = 必做步骤，计打卡。补一张游戏 tab 的原型。

### P1-7 「断开公网」被当成「离线」

- 17.2 验收标准：「**断开公网**后仍可完成主题学习、绘本、拼读和小游戏」

产品是局域网 NAS 架构。断公网但还连着家里 Wi-Fi 时，NAS 完全可达，**这条验收会轻松通过但毫无意义**。

真正的离线验收必须是：关 Wi-Fi / 关 NAS / 带设备出门。

**建议**：改写为「在 NAS 不可达（关闭 NAS 或断开局域网）状态下完成五个步骤，并验证重新接入后自动同步」。T01 写得是对的，17.2 应与之对齐。

### P1-8 录音权限失败时，「跟我说」步骤算不算完成——死锁

- 5.2：跟我说完成条件 = 「完成录音并可回放」；打卡 = 5 类必学步骤全部完成
- 22.3：授权失败时「提供听示范并跳过录音，**不永久阻断任务**」

跳过录音 → 该步骤没有完成事件 → 永远打不了卡。两条规则互相锁死。

**建议**：定义「跳过」的完成语义。建议：记为 `SKIPPED` 状态，满足打卡条件但不发星星（星星绑定录音完成），并在家长中心提示「今日因权限问题跳过录音」。这样既不阻断孩子，也不让奖励规则形同虚设。

## P2 级

### P2-1 录音上传没有接口

12.1、22.3 都写了「家长开启同步录音选项后才上传 NAS」，但 24.2 的接口目录里**没有任何录音上传端点**（11 章的 `/speech/records` 在 24 章被删了）。

需要补：上传端点、大小/时长上限、MIME 白名单、清理任务由谁触发（服务端定时任务还是家长手动）。

### P2-2 多设备学同一课程会导致时长翻倍

8.4、22.4 写的是「学习时长按有效学习会话汇总并**排除重复事件**」。但两台设备各自完成同一步骤，会产生两个**不同的** `eventId`，服务端无法判定为重复事件——`eventId` 幂等只防同一台设备的重试，防不住两台设备各做一遍。

**建议**：时长聚合不要简单求和，改用 `(childId, learningDay, lessonId, stepType)` 去重后取单设备值，或取最大值。

### P2-3 离线包体积完全没有估算

25.3 要求预存「未来 7 天课程 + 最近 5 本绘本」，22.5 让家长设「离线包容量上限」，但全文**没给任何体积参考值**。

5 本绘本 × 8 页高清图 + 7 天音频，很容易到 100–300 MB。平板给孩子的可用空间通常有限。

**建议**：给出单主题 / 单绘本的体积基线，定一个默认上限（如 300 MB），家长中心显示实际占用。

### P2-4 发音评分（A2）与隐私立场冲突，且没进风险表

12.1 的 A2 方案要接第三方 ASR/口语评分，限制栏写「需要公网和调用费用」。

技术上出站请求不违反「NAS 不暴露公网端口」，但它意味着**孩子的录音要上传给第三方**——这与 15 章「录音默认仅存 NAS」「最小数据、最小联网」的立场是冲突的。

28.2 的风险登记表里没有这一条。

**建议**：补进风险表，并明确 A2 是「家长显式开启 + 单独授权」的可选功能，默认关闭。

### P2-5 一堆「合理值」没有数字

- 22.4：「单次会话设合理上限」——上限是多少？
- 8.4：「超过合理时间偏差时提示家长核对」——阈值是多少？
- 12.1：「自动限制单次录音时长」——多少秒？

这类参数不定死，开发各写各的，联调时必然扯皮。

### P2-6 「概率奖励」不适合 5–7 岁

5.2：「今日完成 → 徽章/贴纸**概率奖励**」

可变比率强化是老虎机机制。对 5–7 岁做概率发奖，容易养成「为了抽奖而学习」的动机，而不是「为了学会」。

**建议**：改成确定性奖励（连续 N 天必得徽章），或至少让进度可见（「再学 2 天解锁」）。随机性可以放在贴纸的**图案**上，而不是**是否获得**上。

## P3 级

### P3-1 内容量有三个口径

| 出处 | 词汇 | 绘本 |
| --- | --- | --- |
| 6.1 Level 0 全量 | 300 | 20–40 本 |
| 6.2 推荐首批 | 12 个主题 | — |
| 附录 B 首版 MVP | 30–50 | 3–5 本 |

三个数都对，但并排出现会让读者误判工作量。**建议注明**：6.1 是 Level 0 的长期目标，附录 B 是 MVP 首批交付，6.2 是主题规划池。

### P3-2 7 周工期不现实

27.3：M0–M4 共 7 周，单人兼职。

范围清单：uni-app 双端 15 个页面 + Spring Boot 15 个模块 + 离线 outbox + Push/Pull + 资源包 SHA-256 原子切换 + 日历聚合 + 家长报告 + HTTPS 部署 + 备份演练。

而 27.3 自己已经注明「不包含大量绘本配音、版权整理和云端口语评分」。

**我的判断**：兼职状态下 7 周做到 M2（离线同步跑通）就已经不错，全量 M0–M4 更接近 3–4 个月。28.2 也把「项目范围失控」列为高概率风险——文档自己的风险表已经否定了自己的工期表。

**建议**：把 M0–M2 定为「第一个可用版本」，M3–M4 单独排期，别捆在同一个 7 周计划里。

### P3-3 Compose 示例缺健康检查

13.3 的 `server` 用 `depends_on: - db`，没有 `condition: service_healthy`，`db` 也没有 `healthcheck`。

结果：PostgreSQL 还在初始化时 Spring Boot 就启动了，连接失败退出，靠 `restart: unless-stopped` 反复重启直到成功。能跑，但首次启动慢、日志脏。

**建议**：`db` 加 `pg_isready` healthcheck，`server` 改 `depends_on: { db: { condition: service_healthy } }`。

### P3-4 定版文档里留着「重要更正」勘误段

25.2 末尾有一段「**重要更正**：…`http://NAS-IP` 不属于安全上下文…」。

这说明早期章节（20.6、9.3）写错了，但没回头统一修正，而是在后面打了个补丁。读者看到定版文档里出现勘误，会不知道该以哪段为准。

**建议**：把更正内容合并进 20.6 和 9.3 的正文，删掉勘误段。

### P3-5 目录缺附录

目录列到「28. 技术决策、风险与参考资料」，但正文实际还有附录 A（第一批开发任务拆分）和附录 B（建议首版数据量）。附录 A 的任务拆分是排期依据，应该进目录。

## 汇总

| 级别 | 数量 | 影响 |
| --- | --- | --- |
| P0 | 4 | 数据模型、奖励规则、API 口径、表设计——不动会返工 |
| P1 | 8 | 内部矛盾，必须二选一 |
| P2 | 6 | 细节缺失，开发时会卡 |
| P3 | 5 | 估算与编辑问题 |

**最该先解决的三件事**：

1. **统一 API 口径**（P0-3）——第 11 章和第 24 章只能留一个，这决定了整个后端长什么样。
2. **统一数据模型**（P0-4）——第 10 章和第 23 章只能留一个，这决定了所有表怎么建。
3. **把离线同步前置到 M2**（P1-1）——它决定 M1 的代码要不要重写。

这三件事没定之前，不建议开始写代码。前两件是设计债，第三件是排期债，都是越晚改越贵。
