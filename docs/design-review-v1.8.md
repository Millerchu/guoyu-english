评审日期：2026-10-23。评审对象：[V1.8 详细设计修订稿](设计文档/guoyu-english-detailed-design-v1.8.docx)，覆盖正文 28 章、附录 A/B、接口示例、数据约束和计划测试矩阵。

**结论：整体架构和正常学习链路可以保留，可开展不依赖未决业务规则的工程骨架与平台能力验证；尚不宜把本稿直接冻结为完整开发契约。** 本轮发现 3 项 P1 和 8 项 P2，主要集中在异常恢复、任务版本及统计语义。建议先解决 R01–R03，再在对应模块实施前补齐其余契约。

本文为评审建议，不代表业务决策获批，也未修改原 Word。文首 D01–D07 已明确为待确认选择，本轮不把这些选择本身当作缺陷。以下触发场景是依据设计推演的风险，未宣称已在应用中复现。

## R01 旧备份恢复后同步水位无法重新收敛

**依据：**23.4.1 规定“权威快照仅在 settlementCursor 不小于本地已有版本时应用”；24.5 允许“ACK 后……清理 outbox”；24.5.1 只定义“游标早于保留窗口”的恢复；26.5 又允许恢复数据库备份。

**触发：**备份时服务端水位为 100，随后设备同步到 150 并清理已 ACK 事件。NAS 恢复到 100 后，设备仍带着 150 拉取；重新产生的 101–150 号变更可能被跳过。即使拉完整快照，较小的奖励水位也可能被客户端拒绝。若只检测 `cursor > last_seq`，服务端很快重新增长到 150 后仍可能漏检回退。

这不只是每日备份固有的数据损失窗口，还会造成恢复后的长期分叉。设备撤销等授权状态也可能随数据库回退，需要恢复流程同步处理。

**建议：**同步游标、完整快照和奖励结算增加恢复代次，例如 `streamEpoch`。恢复备份时必须生成新代次，旧代次客户端强制重新获取完整快照，并允许在新代次重置水位。代次不能直接沿用被恢复备份中的旧值。同时明确可接受的数据丢失窗口，以及已 ACK 事件是否保留端侧可重放日志、保留多久；仅增加代次不能找回已被双方删除的事实。

**验收：**客户端已到 150，数据库实际还原到 100，再产生新学习记录；验证能识别代次变化、重建权威缓存、处理未确认记录，且不会跳过恢复后的变化。明确恢复前已确认但未备份的数据如何处理，不能将“数据不丢”写成无条件承诺。

## R02 七天冻结任务与动态续学、时区生效缺少协调协议

**依据：**8.2 写“若前一日未完成：优先继续上一日任务”，并按连续错误安排后续复习；22.4 固定同儿童同学习日唯一任务并冻结版本；22.4.1 要求 NAS 预生成未来七天任务，离线只使用已有快照，同时允许时区修改自下一学习日起生效。

**触发：**周一下载七天任务，周二未完成，周三仍离线。既有周三任务已经固定，客户端不能另造任务，也不能直接把周二事实搬到周三，无法同时兑现动态续学和冻结任务。另一设备修改儿童时区后，离线设备持有的未来任务仍是旧时区版本，也缺少新旧快照的接收规则。

**建议：**先确定业务选择。较小的首版方案是离线按已下载计划学习，续课与错题调度仅影响尚未冻结的新任务，并明确向家长解释；若必须离线自适应，需要设计版本化候选任务或任务修订协议，处理多设备选择、已开始任务及旧版本事件。时区变更另需定义对未来已冻结任务的生效边界，不能仅依靠客户端刷新。

**验收：**离线期间前一天未完成、连续答错、两设备持有不同快照、另一设备修改时区后分别学习再重连；任务归属、打卡与奖励必须有唯一结果。

## R03 空库首次使用缺少创建儿童的接口

**依据：**8.1 要求创建儿童档案；24.7 的 bootstrap 仅“原子创建家庭并返回……parentToken”；24.2 儿童接口只有 `GET/PATCH /parent/children/{id}`，而配对码请求已经需要 `childIds`。

**触发：**全新数据库初始化后没有任何儿童 ID，按唯一接口目录无法创建儿童，也无法为第一个设备签发明确儿童范围的配对码。

**建议：**补充家长权限的儿童创建、列表契约，或明确 bootstrap 同时创建首个儿童并返回 ID。串起“初始化家庭 → 创建儿童 → 生成任务 → 签发配对码 → 首个设备绑定”，明确默认时区、初始版本、重复请求与中断恢复。课程初始化脚本不能默认为真实儿童建档入口。

**验收：**从全新空库完成整个引导，无须人工插入儿童记录；创建请求超时重试不产生重复档案。

## R04 业务时效校验先于去重可能拒绝已成功事件

**依据：**26.3 先执行 `validator.validate(command, principal)`，随后才 `insertIfAbsent` 和 `duplicateResolver`；23.4 也把任务版本校验放在插入前。22.4.1 的自动接收窗口为过去 30 天。

**触发：**接近 30 天边界的事件已提交，但 ACK 丢失；次日重试同一事件，若完整验证器先检查时效，会返回 `TIME_REVIEW_REQUIRED`，而不是已有事件的 `DUPLICATE`。这与 T05 的重复 ACK 承诺不符。旧任务元数据清理后也有同类风险。

**建议：**区分当前身份授权校验、请求结构/摘要校验与仅用于新事件的业务时效校验。在仍有效的设备与儿童授权下，先查既有事件并核对归属和规范化摘要；相同请求返回已提交结果，仅新事件执行当前时间窗口及任务有效性检查。保留并发唯一插入兜底，不允许已撤销设备绕过鉴权。

**验收：**成功提交后丢 ACK，跨 30 天边界或任务元数据保留边界重试，仍能得到正确的重复结果，不重复入账、不错误进入人工修正。

## R05 真实超窗事件没有可执行的家长处理路径

**依据：**22.4.1 对超窗事件要求家长校时或选择正确学习日，再用新 `eventId` 与 `supersedesEventId` 修正；24.2 没有相应审定接口，24.3 没有修正载荷及权限契约；T19 却要求“家长可修正”。

**触发：**真实学习发生在 31 天前，时间本来正确。只换事件 ID 仍然超过 30 天；改成今天则改变历史事实。改正任务日期后，目标还可能不属于该日冻结任务。

**建议：**区分错误时间纠正和真实历史超窗补录。若支持补录，定义家长审定、原始事件留存、修正关联、审计幂等、任务版本及奖励结算窗口；若首版不支持，明确仅保留/导出而不计入权威统计，并修改 T19。不要让客户端靠改日期绕过接收窗口。

**验收：**正确的 31 天前事件和错误时钟事件分别走明确路径；同一人工批准重复执行不重复奖励，原始事实可追溯。

## R06 全部设备凭证丢失后无法恢复管理

**依据：**24.7 规定 bootstrap 成功后永久关闭，已有家长会话又必须由绑定设备持 `deviceToken + PIN` 创建。

**触发：**唯一 H5 浏览器清理数据、全部设备丢失或最后设备被撤销。家长即使记得 PIN，也无法生成新配对码。首次 bootstrap 成功、但尚未配对就关闭页面，待短期会话过期后也可能陷入同样状态。

**建议：**定义只能在 NAS 本地维护终端启动的恢复流程，签发短期一次性恢复凭证，审计恢复动作并明确旧令牌失效策略。不要以重新开放匿名 PIN 登录替代恢复设计。

**验收：**最后设备凭证丢失、首次引导中断、最后设备撤销后，均能通过受控本地流程恢复，儿童档案和学习数据不被重建覆盖。

## R07 录音删除缺少服务端防复活约束

**依据：**24.6 对 PUT 只定义新建和同 ID 同哈希幂等；DELETE 留下删除标记，并通过 Pull 通知其他设备停止重传。没有明确服务端遇到已删除 `recordingId` 的上传应如何处理。

**触发：**上传成功但响应丢失，设备保留上传任务；家长随后删除录音。旧设备在收到删除标记前重试 PUT，或 PUT 与 DELETE 并发，按普通新建路径可能恢复已删除文件。学习事件的 Push 顺序不等于录音队列必然先上传；风险来自缺少服务端拒写规则，单纯调整客户端顺序不能消除竞态。

**建议：**明确删除标记优先，服务端对已删除 ID 原子拒绝重建，定义错误码和客户端终止重试行为。标记保留和完整快照需覆盖长期离线副本；文件、元数据、删除标记与并发写入的处理顺序必须明确。

**验收：**未 Pull 就重试 PUT、PUT/DELETE 并发、增量日志过期后旧设备重连，均不复活录音；同时保持学习完成记录不受文件删除影响。

## R08 备份清单没有明确覆盖私有录音目录

**依据：**13.2/13.3 将 `recordings/` 与 `media/` 分开；第 16 章仍写“PostgreSQL dump + media 目录”恢复，13.6 与 23.5 也未明确私有录音的备份范围。

**触发：**家长开启 NAS 录音同步后，按上述目录备份并恢复，只还原 `speech_record` 元数据而没有录音文件，回放失效。

**建议：**明确可选 NAS 录音是否属于恢复承诺。若属于，将 `recordings/`、元数据、删除标记及一致性校验纳入备份恢复，兼顾删除与备份保留策略；若不属于，写明限制并处理恢复后的悬空引用。

**验收：**使用含一段已上传录音及一条删除标记的备份，在空目录恢复后验证回放、缺失提示与删除状态，而非只确认数据库可启动。

## R09 累计会话时长缺少跨学习日拆分规则

**依据：**22.4.1 按动作 `occurredAt` 归日，同时规定相同 `sessionId` 的 `activeDurationSec` 单调递增并取最大值；23.2 的会话模型没有补充跨日分段契约。

**触发：**同一会话在 23:59 上报累计 120 秒，00:02 上报累计 300 秒。按两个事件日期分别累计会重复此前 120 秒；只保留会话最大值又无法确定两天分别分配多少。

**建议：**学习日边界关闭旧会话并生成新 ID，累计值重新起算；同时明确儿童、任务、步骤与时区版本切换时的会话边界。若允许跨日同会话，则必须携带可独立归档的时段数据。

**验收：**跨午夜、跨月、重复和乱序上报后，两日时长分别正确，总和不重计；两设备合并仍遵循既有最大值规则。

## R10 重试作答与熟悉度及复习规则的判定不唯一

**依据：**5.2 允许识图重试；8.2 按“连续 3 天同一词错误”安排复习；22.4 按“连续两次不同任务中的识图正确且完成一次跟读”判熟悉。24.3 只给跟读完成示例，没有定义识图首次答案和重试顺序的载荷。21.3 的 1/3/7 天复习与纠错复习也未说明合并优先级。

**触发：**孩子每天第一次选错、重试后选对。按最终结果，两天即可熟悉；按首次结果，三天后应进入纠错复习。跨端和服务端都能按当前文字实现出不同结论。

**建议：**明确任务完成、独立掌握与纠错各看哪一次作答。为相关事件定义题目/尝试标识、序号、答案、题目版本和确定性排序；服务端按题目版本判正确性，并定义迟到事件重算规则。补齐复习策略的优先级，不必为此引入新的算法框架。

**验收：**首次错后重试对、跨任务答对、乱序补传、随机选项顺序在 TS 与 Java 得到相同熟悉度和复习计划。

## R11 绘本完成数没有可重建的完成与计次规则

**依据：**8.4 要统计绘本完成数，10.5 要求 `book_count` 可从事件重建；23.4.1 仅定义 `maxCompletedPage` 与 `lastOpenPage`，24.3 虽列 `BOOK_PAGE_READ`，未定义整本完成、重复阅读及归日规则。

**触发：**六页绘本直接跳到第六页读完，最大完成页码已经为 6，但前五页并未读完。跨天阅读或同日重读时，完成数与归档日也无法唯一判定。

**建议：**在 M3 前定义必读页/句集合及版本、整本完成条件、派生完成时间，以及首次完成和重读是否分别计次。最大页码只承担进度提示，不能单独证明整本完成。

**验收：**跳页、倒序阅读、跨日完成、同日重读、多设备分别读部分页面，均能确定性重建阅读进度和 `book_count`。

## 次要一致性修订

- 3.2 仍把绘本、拼读等全部标为“首版上线”；附录 A 把 PIN 放在 M3，而 27.3 将其安排在 M0。27.3 已被明确为唯一里程碑，因此不需要再次选择权威章节，但应同步清理旧任务表，区分最小可用版与后续扩展版。
- T19 要求第八天无快照时可以自由复习，而独立自由游戏页在 M3。明确 M2 可从已下载课程进入 `FREE` 复习的最小入口即可，无须提前开发完整游戏大厅。
- 22.4.1 的可信时间锚点需要在端侧实现设计中补充浏览器重开、进程重启和设备重启后的失效/恢复规则。单调时钟不能直接跨所有运行周期沿用；本轮列为实现前验证点，未判定现有算法已经错误。

## 已明确的设计与待确认选择

V1.8 正文已经写明以下机制，本轮没有将其再次列为缺陷：

- 第 23 章统一持久化模型、第 24 章统一 API，在线与离线学习共用 outbox/Push 链路。
- 按词、句、课程定义奖励业务 key，区分事件 ACK、奖励确认和快照覆盖，避免重复发星。
- 每事件独立事务与家庭流锁、变更页和游标原子落盘、奖励总额与覆盖 key 的一致性视图。
- 麦克风失败显式 SKIPPED、自由游戏不计课程、NAS 不可达的离线验收、可信 HTTPS 和录音授权分离。

D01–D07 仍需要产品确认；300 MiB、30 天、录音时限和排期等仍需实测。本轮新增需要选择的是 R02 的离线任务策略、R05 的历史补录边界，以及 R01/R08 的恢复承诺，不替用户决定这些业务取舍。
